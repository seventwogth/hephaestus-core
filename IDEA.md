Нужно разработать локальную мультиагентную систему на базе Hermes, которая по текстовому описанию пользователя поэтапно создаёт полноценное веб-приложение.

Результатом работы системы должен быть не только набор HTML-, CSS- и JavaScript-файлов, а готовый репозиторий проекта, который можно:

* запустить локально;
* проверить автоматическими тестами;
* развернуть в Docker-контейнерах;
* передать разработчику для дальнейшей доработки;
* позднее опубликовать через отдельный модуль автохостинга.

Примеры приложений, которые такая система должна уметь создавать:

* интернет-магазин с каталогом, корзиной и заказами;
* сервис заметок с регистрацией и авторизацией;
* трекер задач с несколькими пользователями и ролями;
* панель администратора;
* небольшая CRM;
* сервис бронирования;
* приложение с REST API и базой данных.

---

# Общая схема работы

Пользователь взаимодействует с Telegram-ботом. Бот собирает требования и передаёт их оркестратору. Оркестратор разбивает работу на этапы и последовательно запускает специализированных агентов.

```text
Пользователь
    ↓
Telegram-бот
    ↓
Оркестратор
    ↓
Сбор и уточнение требований
    ↓
Проектирование архитектуры
    ↓
Проектирование базы данных
    ↓
Генерация backend
    ↓
Генерация frontend
    ↓
Интеграция компонентов
    ↓
Сборка и тестирование
    ↓
Автоматическое исправление ошибок
    ↓
Формирование готового репозитория
    ↓
Позднее: публикация через модуль автохостинга
```

Главное изменение: результатом считается не опубликованный сайт, а **рабочий проект с воспроизводимым запуском**.

# Что должно входить в готовый проект

Для полноценного приложения система должна создавать примерно такую структуру:

```text
project/
├── README.md
├── SPEC.md
├── PLAN.md
├── TASKS.json
├── STATUS.json

│
├── backend/
│   ├── package.json
│   ├── src/
│   ├── tests/
```

```bash

```

После выполнения команды приложение должно подниматься локально вместе с базой данных.

# Предлагаемый стек

Для первой версии лучше не разрешать модели выбирать любые технологии. Чем больше допустимых стеков, тем выше вероятность несовместимостей и тем сложнее тестирование.

Можно зафиксировать один основной стек:

| Уровень          | Технология                                |
| ---------------- | ----------------------------------------- |
| Frontend         | React + TypeScript + Vite                 |
| Backend          | Node.js + TypeScript + NestJS или Express |
| ORM              | Prisma                                    |
| База данных      | PostgreSQL                                |
| API              | REST                                      |
| Авторизация      | JWT                                       |
| Запуск           | Docker Compose                            |
| Тесты            | Vitest, Jest или Supertest                |
| Документация API | OpenAPI / Swagger                         |

Для MVP я бы выбрал связку:

```text
React + TypeScript
Express + TypeScript
Prisma
PostgreSQL
Docker Compose
```

Express проще для генерации небольшой локальной моделью. NestJS даёт более строгую структуру, но порождает больше файлов и требует от модели лучше удерживать архитектуру проекта.

# Набор агентов

Агенты не обязательно должны быть отдельными постоянно работающими процессами. На практике удобнее использовать один Hermes-runtime, в котором оркестратор запускает разные роли с отдельными промптами и ограниченным контекстом.

## 1. Агент аналитики требований

Его задача — превратить свободное описание пользователя в структурированную спецификацию.

Он должен определить:

* назначение приложения;
* типы пользователей;
* основные пользовательские сценарии;
* страницы интерфейса;
* сущности предметной области;
* необходимые операции;
* требования к авторизации;
* внешние интеграции;
* ограничения;
* критерии готовности.

Пример:

```json
{
  "projectName": "team-task-manager",
  "description": "Сервис для управления задачами команды",
  "actors": [
    "guest",
    "user",
    "admin"
  ],
  "features": [
    "registration",
    "login",
    "create_task",
    "assign_task",
    "change_task_status",
    "filter_tasks",
    "manage_users"
  ],
  "entities": [
    "User",
    "Task",
    "Project"
  ],
  "requiresAuth": true,
  "requiresDatabase": true
}
```

После формирования спецификации пользователь подтверждает её или вносит изменения.

---

## 2. Агент-архитектор

Преобразует требования в технический план.

Он определяет:

* структуру репозитория;
* модули backend;
* структуру frontend;
* формат API;
* таблицы базы данных;
* зависимости между сущностями;
* порядок генерации компонентов;
* критерии проверки каждого этапа.

Результат сохраняется в `PLAN.md`.

Пример фрагмента:

```md
## Backend modules

- auth
- users
- projects
- tasks

## API endpoints

- POST /api/auth/register
- POST /api/auth/login
- GET /api/projects
- POST /api/projects
- GET /api/tasks
- POST /api/tasks
- PATCH /api/tasks/:id
```

---

## 3. Агент проектирования базы данных

Создаёт:

* схему Prisma;
* миграции;
* связи между сущностями;
* ограничения;
* начальные данные;
* тестовые записи.

Пример:

```prisma
model User {
  id           String    @id @default(uuid())
  email        String    @unique
  passwordHash String
  role         UserRole  @default(USER)
  tasks        Task[]
  createdAt    DateTime  @default(now())
}

model Task {
  id          String     @id @default(uuid())
  title       String
  description String?
  status      TaskStatus @default(TODO)
  assigneeId  String?
  assignee    User?      @relation(fields: [assigneeId], references: [id])
  createdAt   DateTime   @default(now())
}
```

После этого выполняется автоматическая проверка миграций.

---

## 4. Агент генерации backend

Реализует серверную часть:

* маршруты;
* контроллеры;
* сервисы;
* DTO;
* валидацию;
* обработку ошибок;
* авторизацию;
* работу с базой данных;
* OpenAPI-документацию;
* базовые тесты API.

Backend должен быть проверяемым отдельно от frontend.

Пример этапа проверки:

```bash
cd backend
npm install
npm run lint
npm run test
npm run build
```

---

## 5. Агент генерации frontend

Создаёт клиентскую часть:

* страницы;
* компоненты;
* маршрутизацию;
* формы;
* API-клиент;
* хранение состояния;
* обработку ошибок;
* адаптивную вёрстку;
* базовые UI-тесты.

Он получает не весь проект, а только:

* `SPEC.md`;
* описание API;
* структуру страниц;
* относящиеся к задаче файлы frontend.

Это уменьшает нагрузку на контекст модели.

---

## 6. Агент интеграции

Проверяет, что frontend и backend действительно совместимы:

* совпадают URL;
* совпадают HTTP-методы;
* совпадают DTO;
* корректно передаются токены;
* обрабатываются ошибки;
* запросы работают после запуска контейнеров;
* CORS настроен правильно.

Он также создаёт общий `docker-compose.yml`.

```yaml
services:
  database:
    image: postgres
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app

  backend:
    build: ./backend
    depends_on:
      - database

  frontend:
    build: ./frontend
    depends_on:
      - backend
```

В реальном проекте конфигурация будет подробнее, но принцип остаётся таким же.

---

## 7. Агент тестирования

Запускает несколько уровней проверок:

| Тип проверки         | Что проверяется                     |
| -------------------- | ----------------------------------- |
| Статический анализ   | TypeScript, линтеры, форматирование |
| Unit-тесты           | отдельные функции и сервисы         |
| Интеграционные тесты | API и база данных                   |
| Smoke-тесты          | запуск приложения                   |
| Контрактные проверки | соответствие frontend и backend     |
| Проверка Docker      | успешная сборка контейнеров         |

Минимальный набор команд:

```bash
docker compose build
docker compose up -d
docker compose ps
docker compose logs
npm run lint
npm run test
npm run build
```

После проверки агент создаёт `REVIEW.md`.

---

## 8. Агент-исправитель

Получает отчёт об ошибках и исправляет только относящиеся к ним файлы.

Пример входного задания:

```text
Ошибка:
POST /api/auth/login возвращает 500.

Лог:
TypeError: Cannot read properties of undefined.

Проверить:
backend/src/modules/auth/auth.service.ts
backend/src/modules/auth/auth.controller.ts
```

После исправления тесты запускаются повторно.

Число циклов нужно ограничить, например:

```text
не более 3–5 попыток на один этап
```

Если ошибка не устранена, оркестратор должен остановить процесс и передать пользователю лог.

---

## 9. Агент документации

Формирует:

* `README.md`;
* команды локального запуска;
* описание переменных окружения;
* тестовые учётные записи;
* описание API;
* известные ограничения;
* инструкции по очистке базы данных.

---

## 10. Агент публикации — позднее

Автохостинг лучше рассматривать не как часть генерации, а как отдельный адаптер.

```text
Готовый репозиторий
    ↓
Deployment Adapter
    ↓
Выбранная платформа
```

В дальнейшем можно добавить несколько стратегий:

| Тип приложения                  | Возможный вариант размещения       |
| ------------------------------- | ---------------------------------- |
| Статический frontend            | GitHub Pages                       |
| Контейнеризированное приложение | VPS                                |
| Frontend + backend              | Render, Railway, Fly.io или аналог |
| Собственная инфраструктура      | Docker Compose через SSH           |
| Более сложная система           | Kubernetes                         |

Оркестратор не должен жёстко зависеть от конкретной платформы. Он просто передаёт готовый проект модулю публикации.

# Как передавать контекст между агентами

Для слабой локальной модели особенно важно отказаться от идеи «пусть несколько агентов свободно переписываются друг с другом».

У агентов должен быть формализованный обмен результатами через файлы.

```text
project/
├── SPEC.md
├── PLAN.md
├── API_CONTRACT.yaml
├── TASKS.json
├── STATUS.json
├── REVIEW.md
├── AGENTS.md
└── DECISIONS.md
```

Назначение файлов:

| Файл                | Содержимое                     |
| ------------------- | ------------------------------ |
| `SPEC.md`           | подтверждённые требования      |
| `PLAN.md`           | архитектура проекта            |
| `API_CONTRACT.yaml` | описание REST API              |
| `TASKS.json`        | список задач и статусы         |
| `STATUS.json`       | текущий этап и число попыток   |
| `REVIEW.md`         | ошибки после тестирования      |
| `DECISIONS.md`      | принятые архитектурные решения |
| `AGENTS.md`         | постоянные правила работы      |

Пример `TASKS.json`:

```json
{
  "tasks": [
    {
      "id": "db-schema",
      "type": "database",
      "status": "done",
      "files": [
        "backend/prisma/schema.prisma"
      ]
    },
    {
      "id": "auth-api",
      "type": "backend",
      "status": "in_progress",
      "files": [
        "backend/src/modules/auth"
      ]
    },
    {
      "id": "login-page",
      "type": "frontend",
      "status": "pending",
      "dependsOn": [
        "auth-api"
      ]
    }
  ]
}
```

Оркестратор при запуске этапа должен передавать агенту:

```text
1. Краткое описание задачи.
2. Только необходимые требования.
3. Список разрешённых для изменения файлов.
4. Результаты предыдущих проверок.
5. Команду, которой проверяется завершённость этапа.
```

```text
  ↓

  ↓

  ↓

  ↓
BACKEND_VALIDATION
  ↓
FRONTEND_GENERATION
  ↓
INTEGRATION
  ↓
BUILDING
  ↓

  ↓
```

# Роль MCP

MCP-сервер по-прежнему нужен, но теперь его функции должны быть шире.

Пример набора инструментов:

```text
create_project()
read_project_state()
save_requirements()
approve_stage()
start_stage()
finish_stage()

read_files()
write_files()
list_changed_files()

run_command()
run_backend_tests()
run_frontend_tests()
run_integration_tests()

run_smoke_tests()

create_git_repository()
commit_changes()
create_branch()
rollback_stage()

get_logs()
save_review_report()

deploy_project()
get_deployment_status()
```

При этом опасные действия нужно ограничить:

* запуск команд только внутри рабочей директории;
* запрет произвольного доступа к файловой системе;
* запрет чтения секретов;
* allowlist разрешённых команд;
* отдельное хранилище токенов;
* подтверждение пользователя перед публикацией;
* лимиты времени и ресурсов для Docker-контейнеров.

# Что считать MVP

Даже после усложнения задачи не стоит сразу пытаться генерировать любые приложения.

Адекватный MVP:

* Telegram-бот;
* один пользовательский проект за один запуск;
* фиксированный стек;
* frontend и backend;
* PostgreSQL;
* CRUD-операции;
* JWT-авторизация;
* Docker Compose;
* генерация миграций;
* базовые API-тесты;
* автоматическая сборка;
* до трёх циклов исправления;
* генерация README;
* локальный запуск;
* без автохостинга.

Пример целевого запроса для MVP:

> Создай сервис учёта книг. Пользователь должен зарегистрироваться, войти в систему, добавлять книги, указывать автора и жанр, менять статус прочтения, редактировать и удалять записи. Данные разных пользователей не должны смешиваться.

Такой проект уже включает:

* базу данных;
* сервер;
* авторизацию;
* REST API;
* frontend;
* формы;
* фильтрацию;
* Docker;
* тестирование.

Это достаточно сложная задача, чтобы продемонстрировать работу мультиагентного подхода, но она всё ещё контролируема.

# Что пока не включать в MVP

Лучше отложить:

* микросервисную архитектуру;
* Kubernetes;
* GraphQL;
* WebSocket;
* OAuth через внешних провайдеров;
* загрузку файлов;
* оплату;
* сложные роли и ACL;
* произвольный выбор фреймворка;
* мобильные приложения;
* автоматическое развёртывание в интернете.

Эти функции можно добавлять поэтапно после того, как система стабильно создаёт обычные клиент-серверные CRUD-приложения.

# Итоговая формулировка идеи

> Разрабатываемая система представляет собой локальный мультиагентный конвейер автоматизированной генерации полноценных веб-приложений. Пользователь формулирует требования через диалоговый интерфейс, после чего агент-оркестратор последовательно запускает специализированные этапы: анализ требований, проектирование архитектуры, создание схемы базы данных, генерацию серверной части, генерацию пользовательского интерфейса, интеграцию компонентов, тестирование, исправление ошибок и подготовку документации.
>
> Система ориентирована на генерацию клиент-серверных приложений с базой данных и воспроизводимым локальным запуском через Docker Compose. Взаимодействие между агентами организуется через структурированные артефакты проекта и общий Git-репозиторий, а не через неограниченный обмен сообщениями. Каждый агент получает минимальный контекст, необходимый для выполнения конкретной задачи.
>
> Автоматическая публикация приложения рассматривается как отдельный расширяемый модуль. Это позволяет сначала сосредоточиться на качестве генерации и проверке проектов, а позднее подключить различные стратегии развёртывания без изменения основной архитектуры системы.
